2. Service (Reglas de Negocio)

2. Modelo Relacional de Base de Datos (SQL DDL Estricto con PK, FK y Tipos)

Esquema PostgreSQL de usuarios, ambientes, inventario, préstamos y novedades. El panel es una consulta derivada; no duplica datos en otra tabla.

-- Esquema PostgreSQL de ControlLabs; bd.sql es la referencia SQL.
CREATE EXTENSION IF NOT EXISTS "pgcrypto";

CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email VARCHAR(255) NOT NULL UNIQUE,
  nombre VARCHAR(150) NOT NULL,
  rol VARCHAR(20) NOT NULL CHECK (rol IN ('ADMIN', 'GUARDA', 'INSTRUCTOR')),
  activo BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE rooms (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  nombre VARCHAR(100) NOT NULL UNIQUE,
  bloque VARCHAR(50) NOT NULL,
  capacidad_pcs INTEGER NOT NULL CHECK (capacidad_pcs >= 0),
  estado VARCHAR(20) NOT NULL DEFAULT 'OPERATIVO'
    CHECK (estado IN ('OPERATIVO', 'MANTENIMIENTO', 'INACTIVO'))
);

CREATE TABLE equipment (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  placa_sena VARCHAR(50) NOT NULL UNIQUE,
  codigo_activo VARCHAR(100) NOT NULL UNIQUE,
  tipo VARCHAR(50) NOT NULL
    CHECK (tipo IN ('COMPUTADOR', 'MOUSE', 'TECLADO', 'CARGADOR', 'TELEVISOR', 'CONTROL_TV')),
  room_id UUID NOT NULL REFERENCES rooms(id) ON DELETE RESTRICT,
  estado VARCHAR(20) NOT NULL DEFAULT 'OPERATIVO'
    CHECK (estado IN ('OPERATIVO', 'MANTENIMIENTO', 'FUERA_DE_SERVICIO'))
);

CREATE TABLE loans (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id UUID NOT NULL REFERENCES rooms(id) ON DELETE RESTRICT,
  instructor_id UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  guarda_id UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  numero_pc INTEGER NOT NULL CHECK (numero_pc > 0),
  estado VARCHAR(24) NOT NULL DEFAULT 'PENDIENTE_APROBACION'
    CHECK (estado IN ('PENDIENTE_APROBACION', 'APROBADO_Y_FIRMADO')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  accepted_at TIMESTAMPTZ,
  CHECK ((estado = 'PENDIENTE_APROBACION' AND accepted_at IS NULL)
      OR (estado = 'APROBADO_Y_FIRMADO' AND accepted_at IS NOT NULL))
);

CREATE TABLE incidents (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  equipment_id UUID NOT NULL REFERENCES equipment(id) ON DELETE RESTRICT,
  reported_by UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  descripcion TEXT NOT NULL,
  prioridad VARCHAR(10) NOT NULL CHECK (prioridad IN ('BAJA', 'MEDIA', 'ALTA')),
  estado VARCHAR(16) NOT NULL DEFAULT 'PENDIENTE'
    CHECK (estado IN ('PENDIENTE', 'EN_PROCESO', 'RESUELTA')),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_equipment_room ON equipment(room_id);
CREATE INDEX idx_loans_room_created ON loans(room_id, created_at DESC);
CREATE INDEX idx_incidents_equipment_status ON incidents(equipment_id, estado);

El esquema no incluye una relación préstamo-equipo: el préstamo conserva la cantidad, pero no identifica activos específicos ni registra su devolución individual.

Prisma ORM: modelo, consultas y responsabilidades

El ORM traduce operaciones tipadas de TypeScript a consultas parametrizadas de PostgreSQL y convierte las filas devueltas a objetos del modelo.

1. Esquema ↔ tablas

prisma/schema.prisma declara modelos, tipos, llaves y relaciones. @@map("loans") y @map("room_id") mantienen el naming de PostgreSQL sin contaminar DTOs y servicios.

2. Cliente tipado

prisma generate crea el cliente con métodos como prisma.loan.create y findMany. No se concatena texto SQL con valores del usuario; Prisma envía parámetros separados.

3. Repositorio

PrismaLoanRepository implementa LoanRepository, traduce el modelo generado al modelo de dominio y propaga fallos desconocidos al middleware global.

Modelo Prisma → tabla existente

model Loan {
  id           BigInt   @id @default(autoincrement())
  roomId       String   @map("room_id") @db.Uuid
  instructorId String   @map("instructor_id") @db.Uuid
  guardaId     String   @map("guarda_id") @db.Uuid
  numeroPc     Int      @map("numero_pc")
  estado       String   @default("PENDIENTE_APROBACION")
  createdAt    DateTime @default(now()) @map("created_at")
  acceptedAt   DateTime? @map("accepted_at")
  room         Room     @relation(fields: [roomId], references: [id])
  instructor   User     @relation("LoanInstructor", fields: [instructorId], references: [id])
  guard        User     @relation("LoanGuard", fields: [guardaId], references: [id])

  @@map("loans")
}

@map cambia el nombre de una columna; @@map cambia el nombre de una tabla. @relation vincula la FK con cada modelo relacionado.

Consultas tipadas usadas por el repositorio

const rows = await prisma.loan.findMany({
  where: roomId ? { roomId } : undefined,
  orderBy: { createdAt: 'desc' }
});

const changed = await prisma.loan.updateMany({
  where: { id: BigInt(id), estado: expectedStatus },
  data: {
    estado: 'APROBADO_Y_FIRMADO',
    acceptedAt: new Date()
  }
});
if (changed.count === 0) return null;

findMany filtra y ordena sin traer toda la tabla a Node. La actualización condicional es una sola operación atómica en PostgreSQL; count distingue una transición aplicada de un registro inexistente o ya aceptado.

No se guarda una URL de conexión en .env. PGHOST es el host/servidor, PGPORT el puerto, PGDATABASE el nombre de la base, PGUSER/PGPASSWORD las credenciales y PGSCHEMA el esquema. Actualiza los valores de ejemplo con tu configuración; si la clave lleva espacios o #, ponla entre comillas en .env. El código la codifica al construir la URL. ¿Quién abre y cierra la conexión?

  1. El módulo compartido src/db/database-url.ts carga dotenv una sola vez y valida los componentes PostgreSQL.
  2. Se crea un único PrismaClient para el proceso; no uno por petición.
  3. Prisma requiere internamente una URL; createDatabaseUrl() la compone en memoria desde las variables y la pasa al cliente/CLI. No se guarda ni se mantiene a mano en .env.
  4. prisma.config.ts usa la misma composición para los comandos CLI. server.ts espera $connect() y solo entonces empieza a escuchar.
  5. Al recibir SIGINT/SIGTERM deja de aceptar peticiones y ejecuta $disconnect().

db:generate genera tipos y cliente, no crea tablas. En una BD existente, respalda y revisa el esquema antes de usar npm run db:pull; puede reescribir schema.prisma. Para una BD nueva, usa migraciones revisadas. No ejecutes migrate dev contra datos productivos.

Errores y reglas: los middlewares validan la forma del body, los UUID y el BIGINT de la ruta, pero no deciden reglas de negocio. El servicio coordina persistencia y mantiene respuestas para registro inexistente/transición ya aplicada; la cantidad no se valida en el servicio. PostgreSQL mantiene claves foráneas y restricciones del esquema. El repositorio traduce P2003/P2004 a errores esperados; los demás fallos llegan a globalErrorHandler y responden 500 genérico.

Tipos importantes: las llaves BIGINT son bigint en JavaScript y no se serializan directamente a JSON. El repositorio las entrega como texto decimal (id: string) para no perder precisión; el controller pasa req.params.id sin convertirlo a Number.

Guía para continuar: módulos, CRUD y reglas de negocio

Una hoja de ruta de diseño para construir los servicios módulo por módulo. Las reglas son propuestas iniciales: confirmarlas con los responsables del proyecto antes de hacerlas obligatorias.

Antes de programar cada módulo

  1. Definir quién puede ejecutar cada acción. En la arquitectura actual aún no hay autenticación; no confiar en un rol recibido en el body.
  2. Definir estados y transiciones permitidas, y qué significa archivar/eliminar.
  3. Definir las relaciones: ambiente ↔ equipo, usuario ↔ préstamo, equipo ↔ novedad.
  4. Separar validación de transporte (middleware) de regla de negocio (servicio).
  5. Escribir ejemplos de éxito y rechazo antes de conectar PostgreSQL.

Estructura sugerida al escalar por módulos

src/
  dtos/              # Contratos de entrada HTTP por recurso
  middlewares/       # Validación del body/query/params y errores HTTP
  controllers/       # Adaptadores Express: request → caso de uso → response
  services/          # Reglas y casos de uso del proyecto
  repositories/      # Interfaces y adaptadores de persistencia
  errors/            # Errores reconocibles por la aplicación
  container.ts       # Punto de composición: crea instancias y las conecta
  routes/            # Endpoints y composición del pipeline

Para un proyecto pequeño, mantener archivos planos es suficiente: user.service.ts, room.service.ts, etc. Si crece, agrupar cada módulo en carpetas (por ejemplo src/modules/users/) ayuda a localizar DTO, controller, service y repository sin crear capas nuevas por moda.

1. Usuarios y roles

Catálogo / identidad

Administra las personas que participan en el control de ambientes: guardas, instructores y administradores. Este módulo no debe tratar el rol declarado por el cliente como una identidad comprobada.

Operaciones sugeridas

POST /users crear; GET /users listar/filtrar; GET /users/:id detalle; PATCH /users/:id editar; PATCH /users/:id/active activar/desactivar.

Preferir desactivación a borrado físico cuando el usuario tenga préstamos o novedades asociados.

Reglas candidatas

  • Email normalizado y único.
  • Rol limitado a ADMIN, GUARDA o INSTRUCTOR.
  • No asignar préstamos ni registrar novedades a usuarios inactivos.
  • El usuario no cambia su rol por sí mismo; autorización requiere identidad autenticada.

Archivos: user.dto.ts + middleware para formato; user.repository.ts y adaptador para persistencia; user.service.ts para unicidad/estado; user.controller.ts y user.routes.ts para HTTP. Errores esperados: duplicado 409, usuario inexistente 404, input inválido 400.

2. Ambientes

Espacios físicos

Mantiene los espacios donde se ubican los activos. El ambiente es una entidad independiente; el inventario mantiene la relación con él mediante una clave foránea.

Operaciones sugeridas

POST /rooms; GET /rooms con filtros; GET /rooms/:id; PATCH /rooms/:id; PATCH /rooms/:id/status.

Evitar DELETE físico si existe historial relacionado.

Reglas candidatas

  • Nombre único y capacidad PC no negativa.
  • Estados controlados: OPERATIVO, MANTENIMIENTO, INACTIVO.
  • Un ambiente no operativo no permite asignar nuevos préstamos.
  • No reducir capacidad por debajo de los equipos instalados.
  • No eliminar mientras tenga activos o préstamos históricos.

Archivos: room.dto.ts, validador de body/query/params, room.repository.ts, room.service.ts, controller y router. La consulta de capacidad instalada depende del repositorio de equipos; la regla de no excederla pertenece al servicio.

3. Inventario y equipos

Activos físicos

Cada equipo representa un activo identificable, no solo una cantidad agregada. Relacionarlo con un ambiente permite conocer ubicación, estado técnico y disponibilidad.

Operaciones sugeridas

POST /equipment; GET /equipment por ambiente/estado; GET /equipment/:id; PATCH /equipment/:id; acción para mover o retirar.

Retirar/archivar conserva el rastro de préstamos y novedades.

Reglas candidatas

  • Código de activo único.
  • Estado limitado a OPERATIVO, MANTENIMIENTO o FUERA_DE_SERVICIO.
  • Solo equipos operativos y disponibles se prestan.
  • Un equipo fuera de servicio no puede asignarse ni trasladarse sin una operación autorizada.
  • El cambio de ambiente debe conservar historial y respetar capacidad.

Archivos: equipment.dto.ts, validadores, repository, service, controller y routes. Al mover un activo, el servicio valida ambiente de destino operativo y capacidad; la persistencia aplica FK y restricciones de unicidad.

4. Préstamos e inventario entregado

Flujo transversal

El flujo ya iniciado en esta sesión. El préstamo registra ambiente, instructor, guarda y cantidad de computadores; ya no enlaza activos concretos. Su aceptación es una transición controlada, no un CRUD genérico.

Operaciones sugeridas

POST /loans; GET /loans por filtros/paginación; GET /loans/:id; PUT /loans/:id/accept; futuras acciones explícitas para devolución/cancelación.

Evitar un PATCH estado arbitrario que salte el flujo.

Reglas de negocio y estado de implementación

  • Implementada: número de PCs entero y mayor que cero; UUIDs de ambiente y usuarios con formato válido.
  • Implementada: el registro nuevo inicia en PENDIENTE_APROBACION.
  • Implementada: solo se acepta desde pendiente; la segunda aceptación produce conflicto.
  • Pendiente de catálogos: verificar que ambiente, instructor y guarda existan y estén activos.
  • No cubierta por este modelo: asociar activos concretos, validar disponibilidad y registrar devoluciones individuales requiere volver a agregar una relación préstamo-equipo o definir un mecanismo alternativo.
  • Pendiente de autenticación: registrar el actor verificado y autorizar al instructor que acepta.
Regla / capa / evidencia Forma del body y tipos → validateLoanPayload → 400 antes del servicio UUID de roomId en búsqueda → validateLoanSearchQuery → 400 BIGINT positivo en la ruta → validateLoanIdParameter → 400 Estado inicial pendiente → PrismaLoanRepository.create Aceptar solo si está pendiente → repository.updateStatus(expectedStatus) → CONFLICT (409) Id inexistente → LoanService.getLoanDetail / acceptLoan → NOT_FOUND (404) Ambiente/personas → aún no verificable; falta consultar catálogos Activos individuales → no quedan asociados con el modelo actual

Archivos siguientes: faltan contratos/repositorios para validar ambiente y usuarios. Obtener guarda desde autenticación, no del body. Si el requisito es rastrear qué activo se presta o su devolución, habrá que diseñar explícitamente una relación alternativa; con este esquema no se puede hacer.

5. Novedades / incidentes

Mantenimiento

Registra problemas ligados a activos y conserva su evolución. Un incidente resuelto no se borra: forma parte del historial del activo.

Operaciones sugeridas

POST /incidents; GET /incidents por estado/prioridad/activo; GET /incidents/:id; PATCH /incidents/:id/status; añadir comentario/solución si se requiere.

No ofrecer borrado normal del historial.

Reglas candidatas

  • Equipo y reportante deben existir.
  • Prioridad y estado usan catálogos cerrados.
  • Transiciones: PENDIENTE → EN_PROCESO → RESUELTA; reabrir requiere acción explícita.
  • Una novedad crítica puede bloquear nuevos préstamos del activo.
  • Resolver exige registrar fecha y responsable.

Archivos: incident.dto.ts, middleware, repository, service, controller y routes. El servicio coordina el cambio de estado del incidente y, si el negocio lo confirma, el bloqueo del equipo; no se debe codificar esa política como supuesto sin validarla con el área responsable.

6. Panel / dashboard

Consulta agregada

Presenta indicadores derivados de usuarios, ambientes, equipos, préstamos e incidentes. En principio es de solo lectura y no debe mantener copias manuales de esos datos.

Operaciones sugeridas

GET /dashboard/summary; GET /dashboard/rooms/:id; GET /dashboard/incidents. No crear CRUD hasta que exista una entidad propia que administrar.

Reglas candidatas

  • Definir numerador, denominador y ventana de tiempo de cada KPI.
  • Contar estados desde las fuentes actuales; no duplicarlos.
  • Aplicar filtros de permisos y ambiente.
  • Mostrar fecha de actualización si los indicadores se cachean.

Archivos: DTO de query si hace falta; dashboard.repository.ts para consultas agregadas; dashboard.service.ts para coordinar indicadores; controller y routes. No se necesita un dashboard.repository de escritura ni tabla duplicada solo para mostrar conteos.

Orden recomendado de implementación

  1. Usuarios e identidad: primero resolver cómo se identifica de forma confiable al guarda/instructor.
  2. Ambientes e inventario: son catálogos requeridos por los préstamos.
  3. Préstamos: alinear el DTO con identificadores de ambiente/usuarios y cantidad; definir aparte si el sistema necesita trazabilidad de equipos.
  4. Novedades: relacionarlas con activos y acordar si ciertos estados bloquean préstamos.
  5. Dashboard: calcular indicadores a partir de los módulos anteriores y acordar sus definiciones.

En cada módulo: escribir primero contrato/DTO y reglas aceptadas; implementar repository y service; conectar controller/routes; probar 201/200, datos inválidos 400, recurso inexistente 404, duplicado o transición incompatible 409 y fallo inesperado 500. Al cambiar de memoria a PostgreSQL, migrar/crear esquema y adaptar el container sin mover reglas al controller.

    PGHOST=localhost
PGPORT=5432
PGDATABASE=controllabs
PGUSER=postgres
PGPASSWORD=REEMPLAZAR_POR_TU_PASSWORD

  "instructorId": "<UUID real de usuario instructor>",

¿Es obligatoria la interfaz? No. Una interfaz TypeScript no existe en tiempo de ejecución y el tipado estructural permite pasar cualquier objeto con esos métodos. Aquí se conserva porque es un contrato pequeño que evita que LoanService importe la clase Prisma y facilita usar un fake en pruebas. La alternativa más corta es tipar el constructor directamente como PrismaLoanRepository; es razonable en un ejemplo de un solo adaptador, a cambio de acoplar el servicio a infraestructura.

roomId, instructorId y guardaId corresponden a las FK del préstamo; numeroPc corresponde a loans.numero_pc. El repositorio Prisma traduce las propiedades camelCase a columnas snake_case; id/fechas/estado no vienen del cliente. El esquema no asigna activos concretos al préstamo. IDs enviados por body son datos de práctica, no identidad confiable; con autenticación, guardaId debe salir de la identidad verificada.

const isUuid = (value: unknown): value is string =>
  typeof value === 'string' &&
  /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i.test(value);

const isCreateLoanDTO = (value: unknown): value is ICreateLoanDTO => {
  if (typeof value !== 'object' || value === null || Array.isArray(value)) {
    return false;
  }

  const loan = value as Record<string, unknown>;
  const allowedFields = new Set([
    'roomId',
    'instructorId',
    'guardaId',
    'numeroPc'
  ]);
  return (
    Object.keys(loan).every((key) => allowedFields.has(key)) &&
    isUuid(loan.roomId) &&
    isUuid(loan.instructorId) &&
    isUuid(loan.guardaId) &&
    typeof loan.numeroPc === 'number' &&
    Number.isInteger(loan.numeroPc)
  );
};

export const validateLoanPayload = (
  req: Request,
  res: Response,
  next: NextFunction

    res.status(400).json({
      success: false,
      error: 'Datos del préstamo inválidos.'
    });
    return;
  }
  next();
};

export const validateLoanIdParameter = (
  req: Request<{ id: string }>,
  res: Response,
  next: NextFunction
): void => {
  const { id } = req.params;
  const isPositiveBigInt =
    /^[1-9]\d*$/.test(id) &&
    id.length <= 19 &&
    BigInt(id) <= 9223372036854775807n;

  if (!isPositiveBigInt) {
    res.status(400).json({
      success: false,
      code: 'VALIDATION_ERROR',
      error: 'El identificador del préstamo debe ser un entero positivo.'
    });
    return;
  }

  next();
};

export const validateLoanSearchQuery = (
  req: Request,
  res: Response,
  next: NextFunction

  const { roomId } = req.query;

    roomId === undefined ||

import { ICreateLoanDTO } from '../dtos/loan.dto';
import { DomainError } from '../errors/domain.error';
import { Loan, LoanFilters, LoanRepository } from '../repositories/loan.repository';

export class LoanService {
  constructor(private readonly loanRepository: LoanRepository) {}

  public createLoan(input: ICreateLoanDTO): Promise<Loan> {
    return this.loanRepository.create(input);
  }

  public getLoans(filters: LoanFilters = {}): Promise<Loan[]> {
    return this.loanRepository.findAll(filters);
  }

  public async getLoanDetail(id: string): Promise<Loan> {
    const loan = await this.loanRepository.findById(id);
    if (!loan) {
      throw new DomainError('NOT_FOUND', `No existe un préstamo con identificador ${id}.`);
    }
    return loan;
  }

  public async acceptLoan(id: string): Promise<Loan> {
    const updated = await this.loanRepository.updateStatus(
      id, 'PENDIENTE_APROBACION', 'APROBADO_Y_FIRMADO'
    );
    if (updated) return updated;
    const current = await this.loanRepository.findById(id);
    if (!current) throw new DomainError('NOT_FOUND', 'No existe el préstamo.');
    throw new DomainError('CONFLICT', 'El préstamo ya fue aceptado.');
  }
}

7. Reemplazar src/middlewares/errorHandler.middleware.ts — conservar el contrato de la Sesión 3 
import { Request, Response, NextFunction } from 'express';
import { DomainError } from '../errors/domain.error';

const domainErrorStatus: Record<DomainError['code'], number> = {
  VALIDATION_ERROR: 400,
  NOT_FOUND: 404,
  CONFLICT: 409
};

export const globalErrorHandler = (
  err: unknown,
  _req: Request,
  res: Response,
  next: NextFunction
): void => {
  if (res.headersSent) {
    next(err);
    return;
  }

  if (err instanceof DomainError) {
    res.status(domainErrorStatus[err.code]).json({
      success: false,
      code: err.code,
      error: err.message
    });
    return;
  }

  if (
    typeof err === 'object' &&
    err !== null &&
    'type' in err &&
    err.type === 'entity.parse.failed'
  ) {
    res.status(400).json({
      success: false,
      error: 'El cuerpo JSON está malformado.'
    });
    return;
  }

  console.error(err);
  res.status(500).json({
    status: 'error',
    message: 'Error interno del servidor en ControlLabs',
    timestamp: new Date().toISOString()
  });

Taller paso a paso: de middleware a servicio y repositorio

Este orden explica cómo se conectan las capas. Los fragmentos parciales sirven para estudiar cada responsabilidad, no reemplazan todos los archivos del repositorio. La ruta ejecutable anterior contiene los pasos de instalación, configuración de PostgreSQL, generación y prueba.

Antes de empezar: identifica las capas que ya existen

src/
  dtos/loan.dto.ts                       existente: contrato de entrada
  middlewares/validateLoan.middleware.ts existente: valida el body HTTP
  controllers/loan.controller.ts         existente: adapta HTTP
  routes/loan.routes.ts                  existente: conecta middleware y controller

No se mueve la validación del body de la Sesión 3 al servicio. Se reutiliza como puerta de entrada y se conectan las capas que faltaban.

Paso 1. Definir el error de aplicación/dominio

src/errors/domain.error.ts — crea este archivo primero. El servicio debe poder expresar “no existe” o “estado incompatible” sin importar Response, códigos HTTP ni Express. El error lleva un código estable; el middleware global decide después qué HTTP enviar.

export type DomainErrorCode = 'VALIDATION_ERROR' | 'NOT_FOUND' | 'CONFLICT';

export class DomainError extends Error {
  constructor(
    public readonly code: DomainErrorCode,
    message: string
  ) {
    super(message);
    this.name = 'DomainError';
  }
}

VALIDATION_ERROR representa una regla de entrada/aplicación incumplida; NOT_FOUND, una entidad que no existe; CONFLICT, una operación válida en forma pero imposible para el estado actual. No es un error de base de datos ni una respuesta HTTP por sí mismo.

Paso 2. Crear el contrato del repositorio

src/repositories/loan.repository.ts define el contrato de operaciones, y prisma-loan.repository.ts lo implementa usando Prisma. El servicio depende de la interfaz y no conoce la base de datos.

  • Loan representa un préstamo ya creado, incluyendo id, estado y marcas de tiempo.
  • LoanStatus limita estados a los valores admitidos: evita actualizar con cualquier texto arbitrario.
  • findById devuelve null cuando no existe: la ausencia es un resultado esperado, no un fallo inesperado.
  • expectedStatus en updateStatus hace una actualización condicional: solo acepta si todavía está pendiente.
export interface LoanRepository {
  create(input: ICreateLoanDTO): Promise<Loan>;
  findAll(filters?: LoanFilters): Promise<Loan[]>;
  findById(id: string): Promise<Loan | null>;
  updateStatus(
    id: string,
    expectedStatus: LoanStatus,
    status: LoanStatus
  ): Promise<Loan | null>;
}

La interfaz no es obligatoria: TypeScript usa tipado estructural y el servicio podría recibir directamente PrismaLoanRepository. Para este ejemplo se conserva el contrato pequeño porque evita que servicio conozca Prisma y permite usar otro adaptador/fake en pruebas. Si el proyecto solo tendrá siempre un adaptador y no necesita esa separación, tipar contra la clase concreta es más corto, pero acopla el servicio a infraestructura.

Paso 3. Conectar PostgreSQL con Prisma ORM

prisma/schema.prisma declara los modelos y mapea propiedades a las tablas existentes. src/db/prisma.ts crea un cliente compartido; PrismaLoanRepository usa consultas tipadas y devuelve el modelo de dominio.

POST /loans → middleware DTO → controller → servicio → PrismaLoanRepository.create → Prisma parametriza INSERT en PostgreSQL → PostgreSQL aplica FK, defaults e ID BIGINT → el repositorio mapea la fila al dominio

Una sola instancia de PrismaClient se crea por proceso, no por petición. La aplicación carga los componentes PostgreSQL desde .env, compone la URL internamente, espera $connect() antes de escuchar y desconecta al cerrar. PostgreSQL conserva los datos y valida las relaciones.

Paso 4. Crear el servicio y sus casos de uso

src/services/loan.service.ts — recibe el contrato LoanRepository y coordina las operaciones, sin conocer Express ni Prisma. Por ahora no agrega validaciones de reglas de negocio al crear/listar: esas reglas quedan aplazadas. Las restricciones estructurales de la base de datos siguen activas.

constructor(private readonly loanRepository: LoanRepository) {}

createLoan(input: ICreateLoanDTO): Promise<Loan> {
  return this.loanRepository.create(input);
}

async getLoanDetail(id: string): Promise<Loan> {
  const loan = await this.loanRepository.findById(id);
  if (!loan) {
    throw new DomainError('NOT_FOUND', `No existe un préstamo con identificador ${id}.`);

  return loan;

Qué hace cada parte: el constructor recibe el repositorio por contrato. createLoan delega sin validar cantidad ni normalizar datos; getLoanDetail busca y convierte ausencia en NOT_FOUND. El id ya llega con formato válido porque validateLoanIdParameter actúa antes del controller. El servicio no construye respuestas HTTP.

Separación con el middleware: validateLoanPayload valida la forma/tipos del body; validateLoanSearchQuery el formato UUID del filtro; y validateLoanIdParameter el entero BIGINT positivo de la ruta. Son validaciones de transporte, no reglas de negocio.

Integridad que se conserva: PostgreSQL todavía exige claves foráneas válidas y aplica sus restricciones CHECK. El repositorio traduce los errores conocidos de esas restricciones; no se agrega una validación de cantidad al servicio.

Responsabilidades del servicio por ahora

  1. Recibe el DTO que ya pasó la validación HTTP.
  2. Delega la creación/listado al repositorio, que usa Prisma.
  3. Traduce el resultado ausente de una búsqueda a NOT_FOUND.

Alcance: la transición de aceptación ya implementada se conserva para no cambiar ese endpoint. Si se quiere posponer también esa regla, conviene dejar la ruta explícitamente en 501 en vez de aceptar transiciones inválidas.

Paso 5. Comprender la aceptación como transición de estado

validateLoanIdParameter comprueba el formato antes de llegar al servicio. LoanService.acceptLoan mantiene el comportamiento que ya tenía el endpoint: solo acepta desde PENDIENTE_APROBACION; si no se actualizó, diferencia inexistente (404) de ya aceptado (409).

const updated = await repository.updateStatus(
  id,
  'PENDIENTE_APROBACION',
  'APROBADO_Y_FIRMADO'
);
if (updated) return updated;

const current = await repository.findById(id);
if (!current) throw new DomainError('NOT_FOUND', 'No existe.');
throw new DomainError('CONFLICT', 'Ya fue aceptado.');

La condición se ejecuta en una única operación condicional de PostgreSQL mediante Prisma updateMany con id y estado esperados. Así dos solicitudes concurrentes no pueden aceptar dos veces el mismo préstamo, incluso con varias instancias del servidor.

Alcance elegido: se aplazan las validaciones de negocio al crear/listar. Se conserva solo la transición de aceptación existente para no cambiar el comportamiento pedido explícitamente; el id se valida en el middleware, no en el servicio.

Falta para la regla de autorización: guardar quién aceptó y comprobar que el actor sea el instructor autorizado. El endpoint actual no tiene autenticación; no debe aceptar un instructorId enviado libremente en el body como prueba de identidad. Esa regla se implementa cuando exista identidad verificada y se pase al caso de uso desde el contexto autenticado.

Paso 6. Conectar las dependencias en un solo lugar

src/container.ts es el punto de composición: el lugar que decide qué implementación usa la aplicación. Actualmente crea el repositorio Prisma e inyecta el contrato en el servicio. No contiene reglas de negocio ni consultas.

Lee la conexión de derecha a izquierda: el repositorio implementa LoanRepository; el servicio recibe esa abstracción y el controller importa el servicio construido. El controller nunca importa Prisma.

¿Por qué un cliente compartido? Prisma administra el pool de conexiones para el proceso. Crear un cliente por petición multiplicaría conexiones y recursos; la instancia se conecta al iniciar y se desconecta en el apagado ordenado.

¿Qué hago cuando agregue los demás módulos?

  1. Crear los componentes del módulo (DTO/validador, contrato de repositorio, adaptador, servicio, controller y rutas) según la operación que necesite.
  2. En container.ts, importar e instanciar el adaptador de ese módulo y pasarlo al constructor de su servicio.
  3. Exportar el servicio construido para que su controller lo use, igual que hace hoy LoanController con loanService.
  4. Montar las rutas del módulo en el router de la API. El container no registra rutas.

const roomRepository = new PrismaRoomRepository(prisma);

Los repositorios de usuarios/ambientes/equipos son una evolución por implementar; el esquema Prisma ya declara esos modelos, pero sus endpoints aún no existen. Comparte el cliente y crea esos adaptadores solo cuando se implementen los casos de uso.

La conexión ya usa PostgreSQL: PrismaLoanRepository implementa el contrato con el cliente compartido. El servicio y el controller no dependen de Prisma ni del driver, solo del contrato de repositorio.

La regla para decidir qué instancia crear vive aquí; las consultas y escrituras viven en el repositorio; las respuestas HTTP viven en el controller. Las reglas de negocio aún no definidas se agregan en el servicio cuando se acuerden.

Paso 7. Hacer que el controlador delegue al servicio

src/controllers/loan.controller.ts — recibe los valores de Express, llama al servicio y transforma el resultado en HTTP. Para crear, retorna 201 Created; para consultar o aceptar, 200 OK. Cada handler async recibe next y delega errores al middleware global.

Paso 9. Traducir errores al protocolo HTTP en un único punto

src/middlewares/errorHandler.middleware.ts — reconoce DomainError y mapea sus códigos a HTTP: VALIDATION_ERROR → 400, NOT_FOUND → 404, CONFLICT → 409. El servicio no conoce esos números; el controller pasa cualquier excepción con next(error).

  • JSON malformado sigue respondiendo 400 (error del parser, no del servicio).
  • Errores desconocidos se registran internamente y responden 500 genérico.
  • Si res.headersSent, se delega con next(err) porque ya no es seguro enviar otra respuesta.

src/app.ts conecta el pipeline: parser/logger y rutas, luego 404 y por último el manejador global. La ruta /__test/error es solo de desarrollo y sirve para comprobar el 500.

Los UUID deben tener formato válido y corresponder a filas existentes; PostgreSQL hace cumplir las FK. Usa el data.id que devolvió POST y envíalo como texto. Reiniciar el servidor no borra préstamos; se almacenan en PostgreSQL.

Recorrido completo de un POST válido
  1. El cliente envía JSON a POST /api/v1/loans.
  2. requestLogger registra la petición; express.json() convierte JSON válido en req.body.
  3. validateLoanPayload comprueba el contrato del DTO. Si falla, contesta 400 y el flujo termina.
  4. LoanController toma el body y llama a loanService.createLoan.
  5. LoanService aplica la regla de negocio y pide la creación al contrato LoanRepository.
  6. PrismaLoanRepository ejecuta el insert; PostgreSQL genera id/estado/fechas y el repositorio mapea la fila.
  7. El controller responde 201 con el recurso creado.

public createLoan(input: ICreateLoanDTO): Promise<Loan> {
  return this.loanRepository.create(input);
}

public async acceptLoan(id: string): Promise<Loan> {
  const updated = await this.loanRepository.updateStatus(
    id, 'PENDIENTE_APROBACION', 'APROBADO_Y_FIRMADO'
  );
  if (updated) return updated;
  const current = await this.loanRepository.findById(id);
  if (!current) throw new DomainError('NOT_FOUND', 'No existe el préstamo.');
  throw new DomainError('CONFLICT', 'El préstamo ya fue aceptado.');
}

La ruta de prueba de error solo se registra fuera de producción y antes del 404. La aceptación todavía no implementa autenticación/autorización; no debe considerarse lista para producción hasta protegerla con una identidad verificada como indica la Sesión 3.
