Sesión 4: implementar la capa de servicios sobre la arquitectura actual

Continuidad de la Sesión 3: el middleware valida el HTTP, el controlador adapta la petición, el servicio aplica reglas y el repositorio persiste.

1. Controller (Express)

Recibe req y res, extrae parámetros (req.params, req.query, req.body) y delega al Servicio.

2. Service (Reglas de Negocio)

Aplica reglas del préstamo (cantidad positiva y transición de estado). No recibe Request/Response, no conoce Express y no se encarga de responder HTTP directamente. Su función es validar la lógica del dominio y lanzar DomainError para que la capa HTTP lo procese más adelante.

3. Repository / DB

Implementa el contrato tipado del servicio. El repositorio usa TypeORM sobre PostgreSQL, así el servicio sigue siendo independiente del motor de datos y solo conoce el contrato del dominio.

CREATE TABLE loans (
  id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id UUID NOT NULL REFERENCES rooms(id) ON DELETE RESTRICT,
  instructor_id UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  guarda_id UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  numero_pc INTEGER NOT NULL CHECK (numero_pc > 0),

DTO de creación alineado por significado, no por el nombre SQL: el contrato HTTP usa camelCase y define los datos que el cliente puede enviar. TypeORM paso a paso: del objeto TypeScript a PostgreSQL

Un ORM (Object-Relational Mapper) conecta dos modelos: los objetos y clases del programa, y las tablas y filas de una base de datos relacional. TypeORM lee los metadatos de las entidades y ofrece APIs de TypeScript para consultar y guardar datos. No elimina SQL: lo genera o lo construye a partir de las operaciones solicitadas y PostgreSQL es quien ejecuta esas consultas.

1. El DataSource configura la conexión

src/config/data-source.ts crea AppDataSource con el driver postgres, los datos de conexión del entorno, el esquema y la lista de entidades conocidas. Al iniciar, server.ts llama a initializeDatabase(); TypeORM establece la conexión y prepara sus metadatos antes de que Express empiece a escuchar peticiones. Si la conexión falla, el servidor no arranca.

export const AppDataSource = new DataSource({
            type: 'postgres',
            host: process.env.DB_HOST ?? 'localhost',
            database: process.env.DB_NAME ?? 'controllabs',
            entities: [LoanEntity]
          });

El DataSource es la puerta de entrada a la configuración de TypeORM. De él se obtiene el repositorio asociado a una entidad; no es una entidad ni guarda por sí mismo cada préstamo.

2. La entidad describe el modelo persistente

LoanEntity es una clase con decoradores que TypeORM interpreta como metadatos. @Entity({ name: 'loans' }) indica la tabla. @PrimaryGeneratedColumn() marca la clave primaria generada; @Column({ type: 'uuid' }) y los demás decoradores describen tipos; @CreateDateColumn marca una fecha de creación administrada por TypeORM. Estas anotaciones describen cómo leer y escribir filas; no contienen las reglas del caso de uso.

En esta entidad, los identificadores UUID se guardan como propiedades escalares. No hay decoradores de relación como @ManyToOne ni @JoinColumn; por tanto, el ORM no modela aquí objetos relacionados de ambiente o usuario. Las claves foráneas y restricciones definidas en PostgreSQL siguen siendo responsabilidad del esquema de la base de datos.

3. El repositorio de TypeORM ejecuta las operaciones

TypeOrmLoanRepository implementa el contrato LoanRepository. En el constructor obtiene un Repository<LoanEntity> desde AppDataSource. Ese repositorio especializado es la API de TypeORM para crear instancias, buscar filas y persistir cambios de la entidad.

Al crear un préstamo, repository.create(...) construye una instancia de LoanEntity en memoria; todavía no realiza una inserción. Después, repository.save(entity) persiste la instancia y espera el resultado de PostgreSQL. El adaptador establece el estado inicial, deja acceptedAt vacío y finalmente convierte la entidad guardada al objeto de dominio que espera el resto de la aplicación.

const entity = this.repository.create({
            ...input,
            estado: 'PENDIENTE_APROBACION',
            acceptedAt: null
          });
          const saved = await this.repository.save(entity);
          return this.toDomain(saved);

Para aceptar un préstamo, el adaptador busca la fila, comprueba que su estado sea el esperado, cambia estado y establece acceptedAt; luego usa save. Si no existe o ya cambió de estado, devuelve null y el servicio decide si corresponde NOT_FOUND o CONFLICT. En esta versión la lectura y el guardado son operaciones separadas; si varias solicitudes pueden aceptar el mismo préstamo simultáneamente, conviene realizar la transición con una actualización condicional atómica o una transacción.

Las lecturas usan findOne para buscar por identificador y createQueryBuilder para construir la consulta filtrada por ambiente. El parámetro :roomId se entrega separado del texto de la consulta, en vez de concatenarse como SQL; así TypeORM puede parametrizar el valor. La conversión toDomain también normaliza las fechas a cadenas ISO, manteniendo el contrato del API independiente de la clase ORM.

4. La separación de capas conserva responsabilidades
  1. El middleware comprueba la forma del JSON HTTP.
  2. El controller entrega los datos del request al servicio y traduce el resultado a una respuesta HTTP.
  3. El servicio valida reglas del dominio y solicita una operación mediante la interfaz LoanRepository.
  4. El adaptador TypeORM usa la entidad y PostgreSQL para leer o guardar datos.
  5. Los errores de negocio se representan con DomainError; los errores inesperados del motor se propagan al middleware global.

TypeORM no reemplaza al servicio, al DTO, a la validación HTTP ni a las restricciones de la base de datos. Por ejemplo, comprobar que numeroPc sea positivo es una regla del servicio; el CHECK de PostgreSQL es una segunda barrera de integridad para los datos persistidos.

5. Esquema y nombres de columnas: revisar antes de ejecutar

En esta solución, synchronize permanece desactivado para evitar que TypeORM altere automáticamente tablas existentes al iniciar. La configuración aún no registra migraciones (migrations: []); por eso, cualquier cambio futuro del esquema debe prepararse y revisarse como una migración explícita antes de ejecutarse.

Mapeo de esta entidad: cada propiedad TypeScript que difiere del esquema declara su nombre SQL mediante name, por ejemplo roomId ↔ room_id y createdAt ↔ created_at. La clave se declara como BIGINT para coincidir con bd.sql; el adaptador convierte el valor devuelto por PostgreSQL al tipo numérico que expone actualmente el contrato de la API. Una migración debe preservar las claves foráneas que dependen de loans.id.

Guía para continuar: módulos, CRUD y reglas de negocio

Una hoja de ruta de diseño para construir los servicios módulo por módulo. Las reglas son propuestas iniciales: confirmarlas con los responsables del proyecto antes de hacerlas obligatorias.

Antes de programar cada módulo

  1. Definir quién puede ejecutar cada acción. En la arquitectura actual aún no hay autenticación; no confiar en un rol recibido en el body.
  2. Definir estados y transiciones permitidas, y qué significa archivar/eliminar.
  3. Definir las relaciones: ambiente ↔ equipo, usuario ↔ préstamo, equipo ↔ novedad.
  4. Separar validación de transporte (middleware) de regla de negocio (servicio).
  5. Escribir ejemplos de éxito y rechazo antes de conectar PostgreSQL.

Estructura sugerida al escalar por módulos

src/
  dtos/              # Contratos de entrada HTTP por recurso
  middlewares/       # Validación del body/query/params y errores HTTP
  controllers/       # Adaptadores Express: request → caso de uso → response
  services/          # Reglas y casos de uso del proyecto
  repositories/      # Interfaces y adaptadores de persistencia
  errors/            # Errores reconocibles por la aplicación
  container.ts       # Punto de composición: crea instancias y las conecta
  routes/            # Endpoints y composición del pipeline

Para un proyecto pequeño, mantener archivos planos es suficiente: user.service.ts, room.service.ts, etc. Si crece, agrupar cada módulo en carpetas (por ejemplo src/modules/users/) ayuda a localizar DTO, controller, service y repository sin crear capas nuevas por moda.

1. Usuarios y roles

Catálogo / identidad

Administra las personas que participan en el control de ambientes: guardas, instructores y administradores. Este módulo no debe tratar el rol declarado por el cliente como una identidad comprobada.

Operaciones sugeridas

POST /users crear; GET /users listar/filtrar; GET /users/:id detalle; PATCH /users/:id editar; PATCH /users/:id/active activar/desactivar.

Preferir desactivación a borrado físico cuando el usuario tenga préstamos o novedades asociados.

Reglas candidatas

  • Email normalizado y único.
  • Rol limitado a ADMIN, GUARDA o INSTRUCTOR.
  • No asignar préstamos ni registrar novedades a usuarios inactivos.
  • El usuario no cambia su rol por sí mismo; autorización requiere identidad autenticada.

Archivos: user.dto.ts + middleware para formato; user.repository.ts y adaptador para persistencia; user.service.ts para unicidad/estado; user.controller.ts y user.routes.ts para HTTP. Errores esperados: duplicado 409, usuario inexistente 404, input inválido 400.

2. Ambientes

Espacios físicos

Mantiene los espacios donde se ubican los activos. El ambiente es una entidad independiente; el inventario mantiene la relación con él mediante una clave foránea.

Operaciones sugeridas

POST /rooms; GET /rooms con filtros; GET /rooms/:id; PATCH /rooms/:id; PATCH /rooms/:id/status.

Evitar DELETE físico si existe historial relacionado.

Reglas candidatas

  • Nombre único y capacidad PC no negativa.
  • Estados controlados: OPERATIVO, MANTENIMIENTO, INACTIVO.
  • Un ambiente no operativo no permite asignar nuevos préstamos.
  • No reducir capacidad por debajo de los equipos instalados.
  • No eliminar mientras tenga activos o préstamos históricos.

Archivos: room.dto.ts, validador de body/query/params, room.repository.ts, room.service.ts, controller y router. La consulta de capacidad instalada depende del repositorio de equipos; la regla de no excederla pertenece al servicio.

3. Inventario y equipos

Activos físicos

Cada equipo representa un activo identificable, no solo una cantidad agregada. Relacionarlo con un ambiente permite conocer ubicación, estado técnico y disponibilidad.

Operaciones sugeridas

POST /equipment; GET /equipment por ambiente/estado; GET /equipment/:id; PATCH /equipment/:id; acción para mover o retirar.

Retirar/archivar conserva el rastro de préstamos y novedades.

Reglas candidatas

  • Código de activo único.
  • Estado limitado a OPERATIVO, MANTENIMIENTO o FUERA_DE_SERVICIO.
  • Solo equipos operativos y disponibles se prestan.
  • Un equipo fuera de servicio no puede asignarse ni trasladarse sin una operación autorizada.
  • El cambio de ambiente debe conservar historial y respetar capacidad.

Archivos: equipment.dto.ts, validadores, repository, service, controller y routes. Al mover un activo, el servicio valida ambiente de destino operativo y capacidad; la persistencia aplica FK y restricciones de unicidad.

4. Préstamos e inventario entregado

Flujo transversal

El flujo ya iniciado en esta sesión. El préstamo registra ambiente, instructor, guarda y cantidad de computadores; ya no enlaza activos concretos. Su aceptación es una transición controlada, no un CRUD genérico.

Operaciones sugeridas

POST /loans; GET /loans por filtros/paginación; GET /loans/:id; PUT /loans/:id/accept; futuras acciones explícitas para devolución/cancelación.

Evitar un PATCH estado arbitrario que salte el flujo.

Reglas de negocio y estado de implementación

  • Implementada: número de PCs entero y mayor que cero; UUIDs de ambiente y usuarios con formato válido.
  • Implementada: el registro nuevo inicia en PENDIENTE_APROBACION.
  • Implementada: solo se acepta desde pendiente; la segunda aceptación produce conflicto.
  • Pendiente de catálogos: verificar que ambiente, instructor y guarda existan y estén activos.
  • No cubierta por este modelo: asociar activos concretos, validar disponibilidad y registrar devoluciones individuales requiere volver a agregar una relación préstamo-equipo o definir un mecanismo alternativo.
  • Pendiente de autenticación: registrar el actor verificado y autorizar al instructor que acepta.

5. Novedades / incidentes

Mantenimiento

Registra problemas ligados a activos y conserva su evolución. Un incidente resuelto no se borra: forma parte del historial del activo.

Operaciones sugeridas

POST /incidents; GET /incidents por estado/prioridad/activo; GET /incidents/:id; PATCH /incidents/:id/status; añadir comentario/solución si se requiere.

No ofrecer borrado normal del historial.

Reglas candidatas

  • Equipo y reportante deben existir.
  • Prioridad y estado usan catálogos cerrados.
  • Transiciones: PENDIENTE → EN_PROCESO → RESUELTA; reabrir requiere acción explícita.
  • Una novedad crítica puede bloquear nuevos préstamos del activo.
  • Resolver exige registrar fecha y responsable.

Archivos: incident.dto.ts, middleware, repository, service, controller y routes. El servicio coordina el cambio de estado del incidente y, si el negocio lo confirma, el bloqueo del equipo; no se debe codificar esa política como supuesto sin validarla con el área responsable.

6. Panel / dashboard

Consulta agregada

Presenta indicadores derivados de usuarios, ambientes, equipos, préstamos e incidentes. En principio es de solo lectura y no debe mantener copias manuales de esos datos.

Operaciones sugeridas

GET /dashboard/summary; GET /dashboard/rooms/:id; GET /dashboard/incidents. No crear CRUD hasta que exista una entidad propia que administrar.

Reglas candidatas

  • Definir numerador, denominador y ventana de tiempo de cada KPI.
  • Contar estados desde las fuentes actuales; no duplicarlos.
  • Aplicar filtros de permisos y ambiente.
  • Mostrar fecha de actualización si los indicadores se cachean.

Archivos: DTO de query si hace falta; dashboard.repository.ts para consultas agregadas; dashboard.service.ts para coordinar indicadores; controller y routes. No se necesita un dashboard.repository de escritura ni tabla duplicada solo para mostrar conteos.

Orden recomendado de implementación

  1. Usuarios e identidad: primero resolver cómo se identifica de forma confiable al guarda/instructor.
  2. Ambientes e inventario: son catálogos requeridos por los préstamos.
  3. Préstamos: alinear el DTO con identificadores de ambiente/usuarios y cantidad; definir aparte si el sistema necesita trazabilidad de equipos.
  4. Novedades: relacionarlas con activos y acordar si ciertos estados bloquean préstamos.
  5. Dashboard: calcular indicadores a partir de los módulos anteriores y acordar sus definiciones.

En cada módulo: escribir primero contrato/DTO y reglas aceptadas; implementar repository y service; conectar controller/routes; probar 201/200, datos inválidos 400, recurso inexistente 404, duplicado o transición incompatible 409 y fallo inesperado 500. Al cambiar a PostgreSQL, migrar/crear esquema y adaptar el container sin mover reglas al controller.

0.1 Reemplazar src/middlewares/validateLoan.middleware.ts — comprobar el DTO real 
import { Request, Response, NextFunction } from 'express';
import { ICreateLoanDTO } from '../dtos/loan.dto';

const isUuid = (value: unknown): value is string =>
  typeof value === 'string' &&
  /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i.test(value);

const isCreateLoanDTO = (value: unknown): value is ICreateLoanDTO => {
  if (typeof value !== 'object' || value === null || Array.isArray(value)) {
    return false;
  }

  const loan = value as Record<string, unknown>;
  const allowedFields = new Set([
    'roomId',
    'instructorId',
    'guardaId',
    'numeroPc'
  ]);
  return (
    Object.keys(loan).every((key) => allowedFields.has(key)) &&
    isUuid(loan.roomId) &&
    isUuid(loan.instructorId) &&
    isUuid(loan.guardaId) &&
    typeof loan.numeroPc === 'number' &&
    Number.isInteger(loan.numeroPc)
  );
};

export const validateLoanPayload = (
  req: Request,
  res: Response,
  next: NextFunction
): void => {
  const body: unknown = req.body;
  if (!isCreateLoanDTO(body)) {
    res.status(400).json({
      success: false,
      error: 'Datos del préstamo inválidos.'
    });
    return;
  }
  next();
};

El middleware verifica los tipos y formato UUID del JSON. No se envían ids de activos porque el esquema ya no vincula equipos con préstamos; la cantidad debe ser un entero positivo y esa regla se conserva en el servicio.

    expectedStatus: LoanStatus,
    status: LoanStatus
  ): Promise<Loan | null>;
}
3. Persistencia real con TypeORM y PostgreSQL en src/repositories/typeorm-loan.repository.ts

Este adaptador implementa el mismo contrato del servicio, pero usa DataSource y Repository de TypeORM para interactuar con PostgreSQL. La lógica del negocio no cambia, solo la forma en que se leen y escriben los datos.

export class TypeOrmLoanRepository implements LoanRepository {
  private readonly repository: Repository<LoanEntity>;

  constructor(dataSource: DataSource = AppDataSource) {
    this.repository = dataSource.getRepository(LoanEntity);
  }

  public async create(input: ICreateLoanDTO): Promise<Loan> {
    const entity = this.repository.create({
      ...input,
      estado: 'PENDIENTE_APROBACION',
      acceptedAt: null
    });

    const saved = await this.repository.save(entity);
    return this.toDomain(saved);
  }

  public async findAll(filters: LoanFilters = {}): Promise<Loan[]> {
    const query = this.repository.createQueryBuilder('loan');
    if (filters.roomId) {
      query.where('LOWER(CAST(loan.roomId AS text)) = LOWER(CAST(:roomId AS text))', {
        roomId: filters.roomId
      });
    }
    const entities = await query.getMany();
    return entities.map((entity) => this.toDomain(entity));
  }
}

El punto clave es que el servicio sigue hablando con LoanRepository, no con SQL ni con el cliente PostgreSQL. TypeORM convierte la entidad a SQL y devuelve objetos del dominio, preservando la separación entre negocio y infraestructura.

4. Crear src/services/loan.service.ts — completo, incluidos sus imports 
import { ICreateLoanDTO } from '../dtos/loan.dto';
import { DomainError } from '../errors/domain.error';
import {
  Loan,
  LoanFilters,
  LoanRepository
} from '../repositories/loan.repository';

export class LoanService {
  constructor(private readonly loanRepository: LoanRepository) {}

  public async createLoan(input: ICreateLoanDTO): Promise<Loan> {
    if (!Number.isInteger(input.numeroPc) || input.numeroPc <= 0) {
      throw new DomainError(
        'VALIDATION_ERROR',
        'El número de PCs debe ser un entero positivo.'
      );
    }

    return this.loanRepository.create({
      roomId: input.roomId.toLowerCase(),
      instructorId: input.instructorId.toLowerCase(),
      guardaId: input.guardaId.toLowerCase(),
      numeroPc: input.numeroPc
    });
  }

  public async getLoans(filters: LoanFilters = {}): Promise<Loan[]> {
    if (filters.roomId !== undefined && !this.isUuid(filters.roomId)) {
      throw new DomainError(
        'VALIDATION_ERROR',
        'El filtro roomId debe ser un UUID válido.'
      );
    }
    return this.loanRepository.findAll({
      roomId: filters.roomId?.toLowerCase()
    });
  }

  public async getLoanDetail(id: number): Promise<Loan> {
    this.validateId(id);
    const loan = await this.loanRepository.findById(id);
    if (!loan) {
      throw new DomainError(
        'NOT_FOUND',
        `No existe un préstamo con identificador ${id}.`
      );
    }
    return loan;
  }

  public async acceptLoan(id: number): Promise<Loan> {
    this.validateId(id);
    const updatedLoan = await this.loanRepository.updateStatus(
      id,
      'PENDIENTE_APROBACION',
      'APROBADO_Y_FIRMADO'
    );
    if (updatedLoan) {
      return updatedLoan;
    }

    const currentLoan = await this.loanRepository.findById(id);
    if (!currentLoan) {
      throw new DomainError(
        'NOT_FOUND',
        `No existe un préstamo con identificador ${id}.`
      );
    }
    throw new DomainError(
      'CONFLICT',
      'El préstamo ya fue aceptado y no puede aceptarse nuevamente.'
    );
  }

  private validateId(id: number): void {
    if (!Number.isInteger(id) || id <= 0) {
      throw new DomainError(
        'VALIDATION_ERROR',
        'El identificador del préstamo debe ser un entero positivo.'
      );
    }
  }

  private isUuid(value: string): boolean {
    return /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i.test(value);
  }
}

7. Reemplazar src/middlewares/errorHandler.middleware.ts — conservar el contrato de la Sesión 3 
import { Request, Response, NextFunction } from 'express';
import { DomainError } from '../errors/domain.error';

const domainErrorStatus: Record<DomainError['code'], number> = {
  VALIDATION_ERROR: 400,
  NOT_FOUND: 404,
  CONFLICT: 409
};

export const globalErrorHandler = (
  err: unknown,
  _req: Request,
  res: Response,
  next: NextFunction
): void => {
  if (res.headersSent) {
    next(err);
    return;
  }

  if (err instanceof DomainError) {
    res.status(domainErrorStatus[err.code]).json({
      success: false,
      code: err.code,
      error: err.message
    });
    return;
  }

  if (
    typeof err === 'object' &&
    err !== null &&
    'type' in err &&
    err.type === 'entity.parse.failed'
  ) {
    res.status(400).json({
      success: false,
      error: 'El cuerpo JSON está malformado.'
    });
    return;
  }

  console.error(err);
  res.status(500).json({
    status: 'error',
    message: 'Error interno del servidor en ControlLabs',
    timestamp: new Date().toISOString()
  });
};

export type DomainErrorCode = 'VALIDATION_ERROR' | 'NOT_FOUND' | 'CONFLICT';

export class DomainError extends Error {
  constructor(
    public readonly code: DomainErrorCode,
    message: string
  ) {
    super(message);
    this.name = 'DomainError';
  }
}

VALIDATION_ERROR representa una regla de entrada/aplicación incumplida; NOT_FOUND, una entidad que no existe; CONFLICT, una operación válida en forma pero imposible para el estado actual. No es un error de base de datos ni una respuesta HTTP por sí mismo.

Qué hace cada parte: el constructor recibe el repositorio, lo que permite sustituirlo sin cambiar el servicio. createLoan valida cantidad positiva, normaliza los UUID de las referencias y delega la persistencia. getLoanDetail rechaza ids no enteros/positivos mediante validateId, busca por id y traduce null a NOT_FOUND. Separación con el middleware: validateLoanPayload valida la forma y el formato UUID del JSON. El servicio aplica la regla del caso de uso: cantidad positiva. Además, valida que el filtro de búsqueda sea un UUID válido.

Límite actual: las reglas de existencia de FK requieren repositorios de ambientes y usuarios; el JSON solo persiste préstamos y no valida esas referencias. El modelo ya no representa activos individuales prestados.

Reglas de creación que sí ejecuta el servicio hoy

  1. Rechaza número de PCs no entero o no positivo.
  2. Normaliza los UUID de ambiente y personas a minúsculas antes de guardar.
  3. Si las reglas pasan, llama al repositorio; este crea el id, inicia el estado pendiente y fija las fechas.

Límite de alcance: el DTO lleva roomId, instructorId, guardaId y numeroPc. Este recurso solo persiste préstamos; todavía no hay repositorios de ambientes/usuarios para verificar existencia y estado. Sin asociación de equipos, no se puede saber qué activos se entregaron o recibieron.

Paso 7. Comprender la aceptación como transición de estado

LoanService.acceptLoan primero valida el identificador con validateId y pide al repositorio cambiar el estado únicamente si el valor actual sigue siendo PENDIENTE_APROBACION. Si no se actualizó, consulta el registro para distinguir dos situaciones: inexistente (404) o ya aceptado/incompatible (409).

const updated = await repository.updateStatus(
  id,
  'PENDIENTE_APROBACION',
  'APROBADO_Y_FIRMADO'
);
if (updated) return updated;

const current = await repository.findById(id);
if (!current) throw new DomainError('NOT_FOUND', 'No existe.');
throw new DomainError('CONFLICT', 'Ya fue aceptado.');

El repositorio TypeORM actual consulta el estado y luego guarda el cambio en una operación separada. Si varias solicitudes intentan aceptar el mismo préstamo al mismo tiempo, conviene implementar la transición como un UPDATE ... WHERE estado = ... atómico o usar una transacción con el aislamiento adecuado.

Reglas aplicadas ahora: id entero positivo; el préstamo debe existir; transición única de pendiente a aceptado; se registra acceptedAt; si ya no está pendiente, se devuelve 409 CONFLICT.

Falta para la regla de autorización: guardar quién aceptó y comprobar que el actor sea el instructor autorizado. El endpoint actual no tiene autenticación; no debe aceptar un instructorId enviado libremente en el body como prueba de identidad. Esa regla se implementa cuando exista identidad verificada y se pase al caso de uso desde el contexto autenticado.

Paso 8. Conectar las dependencias en un solo lugar

src/container.ts es el punto de composición (también llamado composition root): el lugar que decide qué implementaciones concretas usa la aplicación y conecta sus dependencias. No es un contenedor de datos, no guarda préstamos y no contiene reglas de negocio. Con DB_TYPE=postgres, crea TypeOrmLoanRepository y lo inyecta en el servicio bajo el contrato LoanRepository.

import { LoanService } from './services/loan.service';

Lee la conexión de derecha a izquierda: TypeOrmLoanRepository implementa el contrato LoanRepository; el servicio recibe ese repositorio por su constructor; el controller importa el loanService ya construido. El controller no crea repositorios ni decide dónde se persiste.

¿Por qué se crea una sola vez? El módulo se carga al iniciar y todas las peticiones comparten la instancia del DataSource y del repositorio. Eso evita abrir conexiones nuevas por cada request y permite que el ORM haga gestión eficiente de conexiones.

¿Qué hago cuando agregue los demás módulos?

  1. Crear los componentes del módulo (DTO/validador, contrato de repositorio, adaptador, servicio, controller y rutas) según la operación que necesite.
  2. En container.ts, importar e instanciar el adaptador de ese módulo y pasarlo al constructor de su servicio.
  3. Exportar el servicio construido para que su controller lo use, igual que hace hoy LoanController con loanService.
  4. Montar las rutas del módulo en el router de la API. El container no registra rutas.
const loanRepository = new TypeOrmLoanRepository();
export const loanService = new LoanService(loanRepository);

const roomRepository = new TypeOrmRoomRepository();
export const roomService = new RoomService(roomRepository);

El fragmento de usuarios/ambientes/equipos ilustra el patrón para el futuro; crea esos nombres solo cuando existan sus clases reales. La idea es mantener la misma separación de responsabilidades, aunque el adaptador concreto cambie.

¿Y la conexión a PostgreSQL? En la implementación actual se usa un DataSource de TypeORM y la entidad LoanEntity mapea la tabla loans. En el contenedor se construye TypeOrmLoanRepository y se inyecta en el servicio. LoanService y LoanController siguen dependiendo de su contrato, no del driver SQL.

const loanRepository = new TypeOrmLoanRepository();
export const loanService = new LoanService(loanRepository);

La regla para decidir qué instancia crear vive aquí; las reglas de préstamo viven en LoanService; las consultas y escrituras viven en el repositorio; las respuestas HTTP viven en el controller. Esa separación es el objetivo.

  2. requestLogger registra la petición; express.json() convierte JSON válido en req.body.
  3. validateLoanPayload comprueba el contrato del DTO. Si falla, contesta 400 y el flujo termina.
  4. LoanController toma el body y llama a loanService.createLoan.
  5. LoanService aplica la regla de negocio y pide la creación al contrato LoanRepository.
  6. TypeOrmLoanRepository genera id/estado/fechas y devuelve el préstamo desde la base de datos.
  7. El controller responde 201 con el recurso creado.

                      if (!Number.isInteger(input.numeroPc) || input.numeroPc <= 0) {

                      }
                      return this.loanRepository.create({
                        roomId: input.roomId.toLowerCase(),

                        numeroPc: input.numeroPc

public async acceptLoan(id: number): Promise<Loan> {
  const updated = await this.loanRepository.updateStatus(
    id, 'PENDIENTE_APROBACION', 'APROBADO_Y_FIRMADO'
  );
  if (updated) return updated;
  const current = await this.loanRepository.findById(id);
  if (!current) throw new DomainError('NOT_FOUND', 'No existe el préstamo.');
  throw new DomainError('CONFLICT', 'El préstamo ya fue aceptado.');
}

Conexión con la Sesión 3: el validador de payload conserva su respuesta directa 400; los fallos del servicio se lanzan como errores de dominio y Express 5 deriva automáticamente el rechazo del handler async al globalErrorHandler. No se atrapa el error para ocultarlo ni se convierte cualquier fallo en un 404.

Rutas de la API actual: crear préstamo → 201; búsqueda/detalle/aceptación → 200; identificador inválido → 400; inexistente → 404; doble aceptación → 409; fallo inesperado → 500. La ruta de prueba de error solo se registra fuera de producción y antes del 404. La aceptación todavía no implementa autenticación/autorización; no debe considerarse lista para producción hasta protegerla con una identidad verificada como indica la Sesión 3.

Composición actual: src/container.ts inyecta TypeOrmLoanRepository en el servicio. La persistencia real se hace con PostgreSQL usando TypeORM, no con almacenamiento efímero del proceso.

Persistencia actual: el repositorio sigue cumpliendo el contrato LoanRepository, pero la lectura y escritura se realiza contra la base de datos relacional mediante la entidad LoanEntity y el DataSource del ORM.
